# L2 · 软件 ↔ 操作系统——程序不碰硬件，只能「请求」

```
   L0  框架
   L1  软件
 ▶ L2  软件 ↔ OS    ◀ 你在这里
   L3  指令
   L4  数字逻辑
   L5  比特与物理
```

**从上层带下来的问题：** 程序算出了一格格亮度数字，却没点亮屏幕。数字怎么变成光？

**核心思想。** 这是一个让几乎所有初学者惊讶的事实：**你的程序不允许直接碰硬件。** 它不能直接捅屏幕、磁盘、网卡或键盘。那会乱成一团——每个程序都在抢同一个屏幕、同一块磁盘。

相反，有一个特殊的程序永远在运行，它拥有所有硬件：**操作系统**（OS——Windows、macOS、Linux）。其他程序都是客人。客人想让物理世界发生点什么，必须**向 OS 请求**。这个请求叫做**系统调用**。

```
        你的程序（客人）                   操作系统（拥有硬件）
        ──────────────                    ──────────────────
   "这是画面，请帮我画出来"  ──────►  收到请求（"write"）
                                              │
                                              ▼
                                       真正驱动屏幕 ───► 💡 光
   ◄──────────────────────────  "好了"
```

程序活在一个沙盒里。沙盒唯一的出口就是系统调用。画屏幕、读按键、打开文件、发网络包——**每一件**都是程序在礼貌地请求 OS，因为只有 OS 被允许操作真实硬件。

**甜甜圈在这一层。** 还记得我们的「一个后端三张脸」吗？现在可以看到那些箭头到底是什么了——它们都是与 OS 的对话。

两个方向，都经过 OS：

- **输出（向下）：** 终端脸把字符网格变成一个 `write` 系统调用——"OS，请把这些字符放到屏幕上。"桌面和浏览器脸发起各自的绘制请求。后端计算了*想法*；OS 执行了*动作*。
- **输入（向上）：** 当你按下 **→**，你不是"在某个程序里"按键。按键是**OS**先捕获的电事件。OS 判断哪个窗口获得焦点，把事件交给那个窗口，窗口传给后端——后端微调 `state["A"]`，旋转加速。然后新画面再流回去。

这就是三张脸保持同步的原因：只有一个后端持有唯一真实状态，OS 是中转总机，把每条输入路由给它，把每条输出从它路由出去。

> 注意终端不是"瞎子"或二等公民。后端知道终端的尺寸（行×列）和字体，所以它计算整个帧——每个字符**和**每个空白——然后把整帧交给 OS 刷新。终端就是后端绘制的一块画布，跟其他脸一样。同样的想法，不同的单位。

**悬念。** 我们一直在说「OS 做真正的工作」。但 OS 不是魔法——**OS 自己也只是个程序**，一个非常有特权的程序。当 OS 「驱动屏幕」时，它也是在同一个芯片上跑指令。于是我们的问题变得更尖锐，直指下层：当*任何*程序运行——你的还是 OS——它到底在物理上做什么？一个正在跑的程序，底下是什么？→ **L3**

> **一句话旁注。** 当浏览器脸请求一个网页，那个请求离开你的机器，跑到另一台电脑上。这场对话的规则——*计算机网络*——不过是同一个"请别人干活"思路的更大版本。而 OS 同时运行许多沙盒程序的技巧，是*操作系统*课程的核心。
